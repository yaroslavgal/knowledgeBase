## Sync-примитивы

### 22. Mutex — что под капотом `M`
Структура: `state int32` + `sema uint32`. Fast path: атомарный CAS на свободном мьютексе, без syscall. Slow path: горутина в очередь ожидающих, засыпает через `runtime_SemacquireMutex`. С Go 1.9 — starvation mode: если горутина ждёт >1 мс, мьютекс переходит в FIFO.

### 23. RWMutex — когда выигрывает `M`
- Read-heavy (90%+) → значительно быстрее (10x throughput)
- 50/50 → почти одинаково
- Write-heavy → медленнее на ~20% из-за overhead

### 24. ⚡ Двойной Lock на одном мьютексе `M`
**Deadlock на втором Lock**. Рекурсивных мьютексов в Go нет и не будет — это намеренно. Заставляет чинить кривую архитектуру.

### 25. sync.Once `M`
```go
var once sync.Once
var instance *DB
func GetDB() *DB { once.Do(func() { instance = connectDB() }); return instance }
```
Под капотом: атомарный флаг + mutex с double-checked locking. Fast path — только atomic load. Сбросить нельзя — это слом гарантии.

### 26. sync.Pool `M`
Пул переиспользуемых объектов (буферы, большие структуры). Гарантий нет — GC может очистить пул в любой момент. Get не обязан вернуть конкретный объект.

### 27. ⚡ atomic для двух счётчиков? `M`
**НЕТ**, нельзя. Между двумя atomic-операциями может вклиниться другая горутина → несогласованное состояние. Только mutex или упаковка двух полей в одно (2x int32 → int64).

### 28. Когда atomic, когда mutex `M`
- atomic: одна переменная, простые операции (Load, Store, Add, CAS)
- mutex: несколько полей под одним инвариантом, сложная логика, долгая критическая секция
