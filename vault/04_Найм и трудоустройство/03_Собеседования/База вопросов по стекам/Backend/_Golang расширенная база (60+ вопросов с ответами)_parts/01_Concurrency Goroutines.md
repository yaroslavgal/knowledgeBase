## Concurrency / Goroutines

### 1. Горутина vs поток ОС `J`
Горутина — легковесный поток, управляемый Go Runtime (а не ОС). Стек 2-8 KB (поток ~1 MB), переключение в userspace без syscall. Поэтому миллион горутин = 2-8 GB памяти, реально. Миллион потоков — невозможно.

### 2. GMP-модель `M`
- **G** — горутина (стек + состояние)
- **M** — поток ОС (machine)
- **P** — логический процессор с локальной очередью (кол-во = GOMAXPROCS, по умолчанию = ядра)

Каждый M привязан к одному P. У каждого P — локальная очередь горутин до 256, при переполнении — глобальная очередь. **Work stealing**: если очередь P пуста — крадёт половину у соседа.

**Sysmon** — отдельный системный поток, мониторит каждые ~10 мс: вытесняет горутины с >10 мс на P (с Go 1.14), отдаёт P если M застрял на syscall, будит idle M.

### 3. Почему миллион горутин, но не миллион потоков `J`
Поток ОС: 1 MB стек + дескриптор в ядре. Лимит — десятки тысяч. Горутина: 2-8 KB старт + растёт динамически. Когда горутина блокируется на I/O — рантайм паркует её и ставит на M другую. Поток не простаивает (M:N модель).

### 4. ⚡ Что выведет (классика собесов) `M`
```go
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func() { defer wg.Done(); fmt.Println(i) }()
}
```
**Ответ:** `5 5 5 5 5` (на Go до 1.22). Замыкание держит **указатель** на `i`. К моменту старта горутин цикл закончился, `i == 5`.

Фикс: `go func(val int){...}(i)` или `i := i` внутри цикла. С Go 1.22 — переменная цикла per-iteration, баг исправлен.

### 5. Data race vs Race condition `M`
- **Data race** — две горутины одновременно обращаются к одной памяти, хоть одна пишет, без синхронизации. Ловится `go run -race`. UB.
- **Race condition** — логика зависит от порядка выполнения. Может быть БЕЗ data race (например check-then-act под отдельными Lock — TOCTOU).

Data race — подвид race condition. `-race` инструментирует код, overhead 5-10x CPU, 2-3x память. Только в тестах, не в проде.

### 6. counter++ — почему теряется `M`
```go
var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }()  // НЕ атомарно
}
// Результат: 937, 952, 981 — разный
```
`counter++` = read+modify+write. Горутины читают одно значение, инкрементируют, перезаписывают → потеря. Фикс: `atomic.Int64.Add(1)` или `mutex.Lock()`.

`atomic` — для одной переменной (счётчик, флаг, указатель) через CPU-инструкции `LOCK XADD`/`CAS`. `mutex` — когда нужно атомарно изменить несколько полей или сложная логика.

### 7. Find 2 bugs `M`
```go
func processNotifications(notifications []Notification) {
    for _, n := range notifications {
        go func() {
            sendNotification(n) // БАГ 1: замыкание на n
        }()
    }
    // БАГ 2: никто не ждёт горутины
}
```
Фикс: `errgroup.WithContext(ctx)` + локальная копия `n := n` + `g.Wait()`. Почему errgroup лучше WaitGroup: собирает ошибки + отменяет остальные при первой ошибке.

### 8. Worker pool — реализация `M`
```go
func main() {
    jobs := make(chan int, 10)
    results := make(chan int, 10)
    var wg sync.WaitGroup
    for w := 0; w < 3; w++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for job := range jobs { results <- job * job }
        }(w)
    }
    for i := 1; i <= 10; i++ { jobs <- i }
    close(jobs)
    go func() { wg.Wait(); close(results) }()
    for r := range results { fmt.Println(r) }
}
```
Без `close(jobs)` воркеры висят на range. Закрывать results нужно ОТДЕЛЬНОЙ горутиной после Wait — нельзя из main, иначе паника при send.

### 9. Потокобезопасный кэш `M`
```go
type Cache struct {
    mu   sync.RWMutex      // приватное! не embedding
    data map[string]string
}
func (c *Cache) Get(k string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.data[k]
    return v, ok
}
func (c *Cache) Set(k, v string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[k] = v
}
```
RWMutex выигрывает при read-heavy (90%+). При write-heavy может быть медленнее обычного Mutex.

**Антипаттерны:** embedding `sync.Mutex` — пользователь может вызвать Lock() напрямую. Возврат внутреннего слайса/мапы — данные модифицируются без блокировки. Метод Size() внутри Get() с тем же RLock — рекурсивная блокировка → deadlock.

### 10. Go 1.14 — что изменилось в планировщике `M`
До 1.14 — кооперативное планирование: горутина уступала только на yield-точках (I/O, channel, вызов функции). Tight loop `for {}` блокировал поток.

С 1.14 — **preemptive** через async signals (SIGURG). Sysmon мониторит каждые ~10 мс, если горутина занимает P >10 мс — посылает сигнал, рантайм прерывает.

### 11. ⚡ WaitGroup нельзя копировать `M`
```go
// ❌ Plug
func worker(wg sync.WaitGroup) { defer wg.Done() }
// ✅
func worker(wg *sync.WaitGroup) { defer wg.Done() }
```
Все sync-объекты (Mutex, WaitGroup, Cond, Once, Pool) **нельзя копировать**. Копия имеет своё состояние → Done() на копии не уменьшает счётчик оригинала → Wait() висит вечно. `go vet` ловит.
