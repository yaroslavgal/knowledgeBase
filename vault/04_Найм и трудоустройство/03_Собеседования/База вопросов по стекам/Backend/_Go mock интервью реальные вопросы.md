# Mock-интервью Go — реальные вопросы 2026

Q: Тип переменной s := 'Hello'? A: string.

## Junior Go (Mock от Team Lead Ozon)

### Тема: строки и руны

**Q:** Тип переменной `s := "Hello"`?
**A:** `string`.

**Q:** Под капотом строки?
**A:** Массив байт + длина. **Неизменяемый (immutable)**. `s[1] = 'X'` — компилятор не даст.

**Q:** Можно ли сделать `s[1] = 'X'`?
**A:** Нет. Нужен `[]byte(s)` → изменение → `string(b)`.

**Q:** Range по строке — что итерируется?
**A:** **Руны (rune = int32)**, не байты. Даже если строка ASCII.

**Q:** Что выведет `for i, c := range "Привет" { fmt.Println(i, c) }`?
**A:** Индекс байта (0, 2, 4, 6, 8, 10) + код руны (1055, 1088, 1080…).

**Q:** Без `string(r)` — что выведется?
**A:** Числовые значения рун (int32). Чтобы вывести букву — `string(r)`.

### Тема: slice и массив

**Q:** Структура slice в памяти?
**A:** Указатель на массив + len + cap (24 байта на 64-битной архитектуре).

**Q:** Массив vs slice — главное отличие?
**A:** Массив — фиксированная длина, **передаётся по значению**. Slice — динамический, передаётся как header (по сути, по ссылке).

**Q:** Что произойдёт при `append` если cap исчерпан?
**A:** Аллокация нового массива (обычно 2× от текущего cap), копирование, возврат нового slice. Старый slice указывает на старый массив (GC соберёт если нет ссылок).

## Реальные вопросы Cooper (Middle+/Senior)

### Тема: индексы Postgres

**Q:** Какие типы индексов в Postgres?
**A:**
- **B-tree** (default на primary key, foreign keys, обычные WHERE/ORDER BY)
- **Hash** (только для `=`, в Postgres редко используется)
- **GIN** (Generalized Inverted Index — для массивов, jsonb, full-text)
- **GiST** (Generalized Search Tree — для геоданных, диапазонов)
- **Составные** (multi-column) — правило «**до первого неравенства**»

**Q:** Что такое «правило до первого неравенства» в составном индексе?
**A:** Индекс `(a, b, c)` будет использоваться для `WHERE a=1 AND b>5` (используется до колонки b включительно), но не для `WHERE a=1 AND b>5 AND c=3` (после `b>5` — диапазон, c уже не используется).

**Q:** Минусы индекса?
**A:**
- Занимает **место на диске**
- **Замедляет запись** (нужно перестраивать индекс при insert/update/delete)
- При плохо подобранном — может не использоваться (планировщик решает что seq scan быстрее)

### Тема: уровни изоляции

**Q:** Какие уровни изоляции есть?
**A:**
- **Read uncommitted** (грязное чтение разрешено)
- **Read committed** (default Postgres) — видишь только подтверждённые транзакции
- **Repeatable read** — в течение транзакции данные не меняются
- **Serializable** — самый строгий, как будто транзакции по очереди

**Q:** Какие аномалии существуют?
**A:**
- **Lost update** — две транзакции обновляют одно поле, одно обновление теряется
- **Dirty read** — чтение неподтверждённых данных
- **Non-repeatable read** — то же значение возвращается дважды разное
- **Phantom read** — появление новых строк в той же выборке

### Тема: MVCC

**Q:** Как работает MVCC в Postgres?
**A:** Каждая строка имеет `xmin` (транзакция создавшая) и `xmax` (транзакция удалившая). При чтении проверяется видимость по текущему snapshot. Обновление = новая версия с новым xmin. Удаление = установка xmax. VACUUM физически удаляет старые версии.

### Тема: блокировки

**Q:** Оптимистичные vs пессимистичные блокировки?
**A:**
- **Пессимистичные:** `SELECT ... FOR UPDATE` — блокируем строку сразу
- **Оптимистичные:** добавляем поле `version`, при update — `WHERE version = X`. Если 0 строк — кто-то опередил, повторяем

## Топ-вопросы по архитектуре (паттерны Ozon)

### Saga (распределённые транзакции)

**Сценарий:** заказ требует резерв на складе + списание с карты + начисление баллов. Как откатить если хоть один сервис упал?

**Решение:** каждый шаг имеет **компенсирующее действие**. При сбое 3-го шага — откатываем 1 и 2 через компенсации (cancel reservation, refund payment).

### Transactional Outbox

**Сценарий:** сервис должен записать в БД + опубликовать в Kafka. Что если БД ок, а Kafka упал?

**Решение:**
1. В одной транзакции: запись в основную таблицу + запись в `outbox` таблицу
2. Отдельный воркер читает outbox → публикует в Kafka → удаляет из outbox
3. Гарантия доставки **at-least-once**

### CQRS (Command Query Responsibility Segregation)

**Сценарий:** запросы (read) и команды (write) имеют разную нагрузку и форму данных.

**Решение:** разделить модели: командная (нормализованная, write-optimized) + read-модель (денормализованная, read-optimized). Синхронизация через events.

## Концепции которые должен знать каждый Go-Senior

### slice/map/channel/string — внутренности
- **slice header:** `{ptr, len, cap}` — 24 байта
- **string header:** `{ptr, len}` — 16 байт, immutable
- **map:** `hmap` структура, buckets, growing, evacuation
- **channel:** `hchan` структура, mutex + кольцевой буфер

### Memory & GC
- Stack (автоматически освобождается) vs Heap (управляет GC)
- **Escape analysis** определяет куда положить
- GC: trichromatic mark-sweep, **STW <10ms**
- `GOGC=100` (default) — GC запускается когда heap удвоился

### Networking & HTTP
- `net/http` стандартный
- Middleware через handler chains
- Goroutine на каждый request
- Graceful shutdown через signal (SIGTERM/SIGINT)
