# onboard-vault

Проведи владельца через первый setup vault. Это не анкета и не лекция. Это короткое обучение + интервью + проектирование стартовой структуры.

## Читать сначала

- `.vault-agent/RULES.md`
- `.vault-agent/PROFILE.md`
- `.vault-agent/STRUCTURE.md`
- `.vault-agent/STYLE.md`
- `.vault-agent/PATTERNS.md`

Не читай `LESSONS.md`.

## Правила интервью

- Веди onboarding по фазам ниже.
- Задавай 3-5 вопросов за раз, не весь список сразу.
- После каждого блока коротко резюмируй, что понял.
- Если ответ расплывчатый, задай 1-2 уточнения.
- Не соглашайся с чрезмерно сложной структурой. Объясняй риск и предлагай проще.
- Не ограничивай владельца фиксированным числом верхнеуровневых областей. Ограничение не в числе, а в пользе для навигации.
- Не применяй изменения в файлах до финального approval.

## Phase 0 — Preflight

Перед интервью проверь минимальную среду:

1. `AGENTS.md` и `CLAUDE.md` существуют.
2. `.vault-agent/RULES.md`, `PROFILE.md`, `STRUCTURE.md`, `STYLE.md`, `PATTERNS.md`, `LESSONS.md` существуют.
3. `.mcp.json` содержит QMD MCP.
4. `.opencode/opencode.json` содержит QMD MCP.
5. QMD доступен как MCP/search layer.

Если QMD недоступен, не продолжай полноценный onboarding. Коротко объясни, что QMD обязателен для semantic duplicate search и link discovery, и попроси владельца сначала поставить/починить QMD.

Объясни optional Obsidian plugins. Не устанавливай их сам.

Core plugins для базовой ручной работы:

| Plugin | Зачем |
|---|---|
| Backlinks | Входящие ссылки и unlinked mentions. |
| Outgoing Links | Исходящие ссылки и потенциальные links. |
| Page Preview | Быстрый preview заметки по hover. |
| Search | Точный поиск. |
| Quick Switcher | Быстро открыть заметку по имени. |
| Command Palette | Запуск команд Obsidian и plugins. |
| File Recovery | Локальная страховка от случайных изменений. |

Community plugins обсуждай только после базовой структуры:

| Plugin | Когда предлагать |
|---|---|
| Obsidian Git | Нужен backup/version history через GitHub из Obsidian. |
| Editing Toolbar | Владелец не хочет писать Markdown руками. |
| Recent Files | Нужен быстрый возврат к последним заметкам. |
| Homepage | Нужен стартовый MOC/home screen. |
| Templater | Появились стабильные note templates. |
| QuickAdd | Появились повторяемые capture/create workflows. |
| Image Zoom & Drag | Много Mermaid/изображений/диаграмм. |

Не предлагай по умолчанию:

- Auto Note Mover — может двигать заметки без agent approval;
- Linter — может массово переписать formatting;
- Dataview — полезен для query views, но добавляет сложность;
- Manual Sorting — личный UI-порядок;
- Book Search, Contribution Graph, theme/settings plugins — domain/UI-specific.

## Phase 1 — Объяснить модель

Объясни простым языком:

| Термин | Объяснение |
|---|---|
| Vault | Папка Markdown-файлов. Obsidian показывает их как базу знаний. |
| Заметка | Минимальная единица знания. Обычно одна заметка держит одну основную мысль, источник, проект или карту. |
| MOC | Map of Content. Это вход в область и маршрут чтения, не автоматический список файлов. |
| `parent` | Главная карта/MOC, к которой относится заметка. Помогает агенту и человеку понимать место заметки. |
| `description` | Плотная строка для поиска и disambiguation. Агент использует её как индекс. |
| Inline link | Ссылка прямо в тексте, если она естественно встроена. Это приоритетный вариант. |
| Related link | Связь в отдельном блоке, когда relation относится ко всей заметке или требует комментария. |
| QMD | Semantic search по vault. Нужен, когда слова отличаются, но смысл похож. |

Коротко объясни runtime:

| Слой | Что делает |
|---|---|
| Skills | Основные рабочие сценарии: создать заметку, улучшить, найти links, проверить vault, обновить правила. |
| Commands | Короткие OpenCode-входы к skills: `/onboard`, `/check`, `/learn`, `/reflect`. В Claude Code используй обычный запрос или название skill. |
| Read-only agents | Помощники для поиска кандидатов и review. Они читают и предлагают, но не редактируют файлы. |

Скажи владельцу базовую установку:

```text
Папки дают грубую область.
MOC даёт маршрут.
parent даёт основной навигационный указатель.
links дают смысловые связи.
QMD помогает найти то, что обычный поиск пропускает.
```

## Phase 2 — Цель vault

Спроси:

1. Для чего ты хочешь использовать Obsidian сейчас?
2. Что должно стать легче через месяц?
3. Что должно стать легче через 6 месяцев?
4. Что сейчас самое медленное: найти старую мысль, разложить новое, связать идеи, вести проекты, работать с источниками?
5. Какие 3-5 запросов ты хотел бы задавать агенту внутри vault?
6. Нужен ли Git/GitHub backup для истории изменений и сохранения vault?
7. Какие plugins включаем сейчас: только core минимум, Git backup, удобство редактирования, шаблоны/capture, диаграммы — или пока не трогаем plugins?

После ответа заполни draft для `PROFILE.md`:

- why this vault exists;
- one-month goal;
- six-month goal;
- current friction;
- real agent use cases.
- backup/versioning preference.
- optional Obsidian plugin preference.

## Phase 3 — Материалы и типы заметок

Объясни минимальные note types:

| type | Когда использовать |
|---|---|
| `concept` | Одна мысль, модель, принцип, механизм. |
| `source` | Статья, книга, видео, подкаст, transcript. |
| `reference` | Справка, человек, продукт, место, ресурс, обзор. |
| `map` | MOC / навигационная карта. |
| `project` | Активная работа, решения, контекст, next actions. |
| `capture` | Сырой материал, который ещё не оформлен. |

Спроси:

1. Какие материалы будут появляться чаще всего?
2. Что должно становиться отдельной заметкой?
3. Что лучше сначала складывать как `capture`?
4. Будут ли проекты внутри vault?
5. Нужны ли заметки про людей, источники, процессы, решения?

Зафиксируй в `PROFILE.md` material types и первые rules для `STRUCTURE.md`.

## Phase 4 — Поиск и навигация

Спроси:

1. Как ты обычно вспоминаешь информацию: название, тема, ситуация, человек, проект, смысл?
2. Какие реальные поисковые запросы ты ожидаешь задавать?
3. Где тебе удобнее входить в область: папка, MOC, поиск, backlinks?
4. Какие области без карты быстро станут неудобными?

Объясни:

- `description` помогает агенту находить и отличать заметки;
- aliases нужны для сокращений, альтернативных названий и языковых вариантов;
- QMD не заменяет чтение заметок, а даёт candidates.

## Phase 5 — Стартовая структура

Спроси:

1. Какие крупные области уже видны?
2. Какие из них будут расти регулярно?
3. Где нужна папка, потому что область стабильная?
4. Где достаточно MOC без отдельной папки?
5. Какие области могут пересекаться и не должны становиться вложенными папками?

Проверь предложения владельца:

- если область слишком широкая, предложи MOC sections;
- если область слишком узкая, предложи не делать отдельную папку;
- если структура строится "на всякий случай", предложи отложить;
- если есть 2-3 похожих области, предложи одну карту с секциями.

Output для `STRUCTURE.md`:

- top-level areas;
- folder candidates;
- first MOCs;
- parent policy;
- open structure questions.

## Phase 6 — Связи

Объясни:

```text
Ссылка нужна не потому, что две заметки похожи.
Ссылка нужна, когда будущему читателю понятно, зачем открыть вторую заметку из первой.
```

Default policy:

- inline link first, если ссылка естественно встраивается в текст;
- related link с комментарием, если связь относится ко всей заметке;
- bare related links запрещены;
- generic hubs требуют конкретного механизма;
- QMD даёт candidates, но link подтверждается чтением обеих заметок.

Спроси:

1. Какие связи будут полезны: причина, применение, пример, контраст, часть системы, источник?
2. Какие связи точно не нужны?
3. Какие широкие темы могут стать мусорными hubs?

Запиши link preferences в `STRUCTURE.md` или `PATTERNS.md`.

## Phase 7 — Стиль и visual flow

Спроси:

1. На каком языке писать разные типы заметок?
2. Что раздражает: длинные summaries, академичность, AI-prose, слишком много таблиц, слишком мало структуры?
3. Когда нужен TL;DR?
4. Где нужны Mermaid diagrams, tables, checklists?
5. Какие заметки позже можно будет считать good examples?

Не фиксируй слишком много style rules сразу. Стартовый `STYLE.md` должен быть нейтральным, а реальные preferences появятся через `LESSONS.md`.

## Критерий хорошего onboarding

После onboarding должно быть понятно:

- зачем существует vault;
- какие материалы туда попадают;
- как владелец будет искать;
- какие первые области и MOC нужны;
- как работает `parent`;
- как ставятся links;
- какой стиль использовать пока;
- что делать дальше.
