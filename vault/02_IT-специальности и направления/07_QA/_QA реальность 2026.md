# QA — реальность 2026

QA — самый низкий порог входа в IT и одна из самых забитых ниш. Если цель «войти быстро без бэкграунда» — QA Manual работает. Если цель «зарплата 400к+» — QA Automation, но это де-факто разработка.

## Реальность 2026

**Вакансии:** ~1859 в крупных компаниях — самый объёмный сегмент по абсолюту.

**Конкуренция:** запредельная на manual, умеренная на automation.
- На одну Manual-вакансию приходит ~50–80 резюме.
- На одну Automation-вакансию ~20–40 резюме.

**Зарплаты в Москве 2026:**

| Тип | Стажёр | Junior (мало вакансий) | Middle | Senior |
|---|---|---|---|---|
| QA Manual | 0–40к | 40–100к | 80–180к | 150–280к |
| QA Automation (SDET) | 0–50к | 70–150к | 150–300к | 300–500к |

**Тренд:** Manual постепенно падает (AI закрывает базовые регрессии), Automation растёт. Через 3–5 лет рассчитывать на чистый Manual как профессию рискованно.

## Manual vs Automation — ключевое различие

### QA Manual
- Прохождение тест-кейсов руками.
- Заведение баг-репортов с шагами воспроизведения.
- Smoke / regression / exploratory тестирование.
- Работа с тест-планами, тест-документацией.
- Часто — UAT (приёмочное тестирование).

**Стек Manual:**
- Postman / Insomnia / Bruno (API тестирование).
- Charles / Fiddler / Proxyman (анализ траффика).
- Chrome DevTools.
- Jira / TestRail / Allure.
- Базовый SQL (читать данные).
- Базовый Linux (логи).

### QA Automation (SDET)
- Пишет автотесты — фактически разработчик с уклоном в тестирование.
- E2E тесты (Playwright, Selenium, Cypress).
- API тесты (REST Assured, pytest + requests).
- Mobile-тесты (Appium, XCUITest).
- Performance тесты (JMeter, Gatling, k6).
- Setup CI/CD pipelines для тестов.

**Стек Automation:**
- Один язык: **Python** (pytest), **JavaScript/TypeScript** (Playwright/Cypress), реже Java/Kotlin (REST Assured, Selenium WebDriver).
- Понимание HTTP, REST, WebSockets.
- SQL.
- Docker, базовый CI/CD.
- Allure для отчётов.
- Базовый Git.

## Когда брать QA как стратегию

### Бери QA Manual, если:
- Нет программирования вообще, нужен быстрый вход в IT.
- Аналитический склад ума (любишь искать баги, ломать продукт).
- Готов к низкому потолку (180–280к для middle/senior).
- Через 1–2 года планируешь перейти в Automation или другую роль.

### Бери QA Automation, если:
- Уже знаешь основы программирования.
- Хочешь быть «разработчиком, который пишет тесты».
- Зарплаты до 500к — приемлемый потолок.
- Готов к 6–9 месяцам подготовки (как backend).

### НЕ бери QA, если:
- Хочешь зарплаты 400к+ через 2–3 года → backend (Go) даст быстрее.
- Хочешь creative работу → разработка интереснее по задачам.
- Не готов к рутине (manual особенно).

## Стратегия Manual → Automation (популярный путь)

Большинство Automation-инженеров пришли из Manual за 1–2 года.

**Год 1: Manual:**
- Устраиваешься в Manual за 80–120к.
- Изучаешь продукт, баги, процессы тестирования.
- Параллельно учишь программирование (Python или JS).

**Месяцы 12–18:**
- Внутри компании просишь автотесты как часть задач.
- Пишешь первые автотесты для своих ручных кейсов.
- Через полгода — половина задач уже автоматизация.

**Месяцы 18–24:**
- Переход внутри компании на SDET (или внешний оффер) с +50–100к зарплаты.
- Через 2 года middle Automation 200–300к.

## Реалистичный путь входа

Канон обучения — через практику с AI. Никаких лекций «впрок». AI как ментор 24/7. См. [[01_Образование и обучение/06_Менторы и AI-обучение/_Философия обучения через практику|Философия обучения через практику]].

### QA Manual (с нуля 2–4 мес)

**Месяц 1: основы**
- Что такое баг, как его описывать (шаги, ожидаемое, фактическое, severity, priority).
- Виды тестирования (functional, regression, smoke, sanity, exploratory).
- Тест-дизайн: equivalence partitioning, boundary value, decision tables.
- ISTQB Foundation материалы (бесплатные).

**Месяц 1–2: инструменты**
- Postman: как тестировать REST API (методы, статус-коды, headers, body).
- Chrome DevTools: Network, Console, Application.
- Charles или Fiddler: перехват HTTPS-трафика, throttling.
- Jira / любой issue tracker: создание баг-репортов.
- Базовый SQL: SELECT, JOIN, WHERE.

**Месяц 2–3: пет-проект**
- Берёшь публичное API (например, GitHub API) или открытое веб-приложение.
- Пишешь тест-план (10–20 кейсов).
- Прогоняешь, заводишь баги в свой Jira.
- Делаешь скриншот-отчёт для портфолио.

**Месяц 3–4: подготовка к собесу + поиск**
- Банк типовых вопросов QA Manual.
- Параллельный поиск 15–20 компаний.

### QA Automation (с нуля 6–9 мес)

**Месяц 1–3: программирование**
- Python (или JS/TS) до уровня «могу написать утилиту 100 строк».
- ООП basics (классы, наследование).
- Понимание тестов (assertions, fixtures, setup/teardown).

**Месяц 3–4: тестовые фреймворки**
- pytest (Python) или Jest/Vitest (JS).
- Структура тестов: unit / integration / e2e.
- Параметризация, фикстуры.

**Месяц 4–6: E2E + API**
- Playwright или Cypress: e2e-тесты для веб-приложения.
- REST Assured (Java) или pytest + requests (Python) или Supertest (JS): API-тесты.
- Allure отчёты.

**Месяц 6–9: продакшен-уровень + поиск**
- Один полный test-suite на пет-проект (e2e + API + unit).
- CI/CD: GitHub Actions с прогоном тестов на каждый PR.
- Параллельный поиск middle SDET-вакансий.

## Темы, которые точно спросят на middle-собесе

### QA Manual
- Виды тестирования и когда какое применять.
- Severity vs Priority — разница, примеры.
- Boundary value analysis на конкретной задаче.
- Регрессионное тестирование: ручное vs автоматизированное.
- Чем отличается smoke от sanity.
- Как тестировать API без UI: Postman, Charles.
- Как составить тест-кейс для формы регистрации (поля, валидации, негативные).
- Что проверить при тестировании авторизации.
- HTTP-коды: 401 vs 403, 200 vs 201, 502 vs 503.
- Что такое idempotency и почему важно.

### QA Automation
- Page Object Model: что это, зачем, плюсы/минусы.
- Flaky tests: как ловить, как чинить.
- Test pyramid: unit / integration / e2e — соотношения.
- Parallel execution: как организовать.
- Test isolation: как избежать межтестовых зависимостей.
- Mocking vs Stubbing vs Faking — разница, примеры.
- Continuous Testing: как встроить в CI/CD.
- Selenium vs Playwright vs Cypress — плюсы/минусы.
- Performance тестирование: load vs stress vs spike vs soak.
- Test data management: как генерировать, изолировать.

## AI на работе QA: ~25–30% автономно

В QA AI закрывает чуть больше рутины, чем в backend (~25–30%):
- Генерация тест-кейсов по описанию фичи.
- Boilerplate для page objects, fixtures.
- Конвертация ручных кейсов в автотесты.
- Объяснение сложных багов в стектрейсах.
- Подсказки по селекторам Playwright/Selenium.

Что AI **не делает:**
- Exploratory testing — нужна человеческая интуиция и контекст.
- Reproducibility сложных багов (race conditions, browser-specific).
- Решение про test architecture (что unit, что integration, что e2e).
- Анализ flaky tests — нужен контекст системы.

## Антипаттерны

❌ **Идти в QA, чтобы потом перекатиться в разработку.** Перекаты случаются, но это лишний год-два по сравнению с прямым входом в backend.
**Решение:** если цель — разработка, иди сразу туда.

❌ **Учить Selenium как первый automation-инструмент.** Selenium — legacy, в новых проектах редко берут.
**Решение:** Playwright или Cypress (для веба), Appium (для mobile).

❌ **Игнорировать программирование на Manual.** Через год Manual без программирования = тупик. Будут увольнять, заменять автоматизацией.
**Решение:** с месяца 6 на Manual параллельно учи Python.

❌ **Надеяться, что портфолио на GitHub откроют.** Не откроют. Тест-план или автотесты нужны для рассказа на собесе своими словами, а не для красивой витрины.
**Решение:** один пет-проект тест-плана + один пет-проект автотестов — для собственного опыта и собесного рассказа.

❌ **Учить ISTQB как самоцель.** Сертификат полезен только для базы. На зарплату не влияет почти никак.
**Решение:** прочитать материалы (бесплатно), сертификат покупать только если работодатель компенсирует.

## Чек-лист готовности к middle-собесу QA

### Manual
- [ ] Виды тестирования и когда применять.
- [ ] Тест-дизайн техники (boundary, equivalence, decision tables) на практике.
- [ ] Postman: тестирую REST API с auth, переменными, скриптами.
- [ ] Chrome DevTools: Network, Console — без подсказок.
- [ ] SQL: могу написать запрос с JOIN и WHERE для проверки данных.
- [ ] Jira / TestRail: создание баг-репортов с правильной структурой.
- [ ] Один пет-проект тест-плана (10–20 кейсов на публичном API).
- [ ] Базовый Linux: чтение логов, grep.

### Automation
- [ ] Один язык (Python / JS / TS) на уровне «могу написать утилиту с тестами».
- [ ] pytest / Jest до уровня fixtures, parametrize, plugins.
- [ ] Playwright или Cypress: e2e-тесты с Page Object Model.
- [ ] API-тесты: pytest + requests или Supertest.
- [ ] CI/CD: GitHub Actions с прогоном тестов.
- [ ] Allure отчёты.
- [ ] Один пет-проект полного test-suite — для рассказа на собесе, не для GitHub-витрины.
- [ ] Понимаю flaky tests и стратегии стабилизации.
- [ ] Базовый Docker.
- [ ] Базовый SQL и Linux.
